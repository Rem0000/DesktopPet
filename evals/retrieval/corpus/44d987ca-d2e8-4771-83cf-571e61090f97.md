

# 数据库三范式

第一范式：列不可再分

第二范式：行可以唯一区分，主键约束

第三范式：除主键外的其他列必须和主键直接相关，不能间接相关，外键约束

# InnoDB 和 MyISAM 的区别

## 事务区别

InnoDB 支持完整的 ACID 事务（原子，一致，隔离，持久）。这是 InnoDB 最核心的优势之一。它允许你将一组 sql 操作作为一个不可分割的工单单元来执行。如果其中任何一条语句执行失败，整个事务可以回滚，保证数据处于一致状态。

 MyISAM类型的表强调的是性能，其执行数度比InnoDB类型更快，但是不提供事务支持。

## 锁机制

InnoDB 默认采用行级锁，写操作的时候只锁定一行。

MyISAM 只支持表级锁，写操作的时候会锁定整个表。

## 外键约束

InnoDB 支持外键约束

MyISAM 不支持

## 崩溃恢复

InnoDB 具有强的的崩溃恢复能力。采用 WAL 机制。所有修改在应用到数据文件之前，会先持久化写入到重做日志(RedoLog)文件。如果数据库意外崩溃（如服务器断电），重启时 InnoDB 可以利用 RedoLog 自动重做崩溃前
已提交但尚未写入数据文件的更改，并利用 UndoLog 回滚未提交的事务，从而保证数据的持久性（Durability）和一致性。这个过程通常是自动且可靠的。

MyISAM: 崩溃恢复能力较弱。它没有事务日志（如 Redo Log）。

## 存储结构

InnoDB 是聚集索引，数据文件是和索引绑定在一起的，必须有主键，通过主键索引效率很高。

MyISAM 索引和数据是独立的

# RedoLog 和 Undolog



在 MySQL 的 **InnoDB 存储引擎** 中，**Redo Log（重做日志）** 和 **Undo Log（回滚日志）** 是保障事务 **ACID 特性** 的核心日志组件，二者分工明确、协同工作：

- **Redo Log**：保障 **事务持久性**，解决「宕机后已提交事务不丢失」的问题；
- **Undo Log**：保障 **事务原子性 + 一致性**，解决「事务失败可回滚 + 多版本并发读（MVCC）」的问题。

## 一、Redo Log

### 1. 核心作用

**记录「事务对数据做了什么修改」**，用于 **崩溃恢复**：

MySQL 重启后，若事务已经提交，但数据还没来得及写入磁盘，就通过 Redo Log 把修改 **重做** 一遍，保证「提交的事务永久生效」。

**`Redo Log记录包含已经提交的事务修改记录以及没提交的事务的修改记录`**



### 2. 核心原理：WAL 预写日志机制

<span style="color:#CC0000;">这是 Redo Log 的灵魂：**先写日志，再写磁盘**</span>。

- MySQL 操作数据时，优先修改 **内存（Buffer Pool）** 中的数据（速度极快）；
- 不直接修改磁盘数据文件（随机 IO，极慢），而是先把修改记录写入 Redo Log；
- 后台线程异步将内存的脏数据刷入磁盘。

### 3. 完整工作机制

Redo Log 由 **两部分** 组成：

1. **Redo Log Buffer**：内存缓冲区，临时存储日志；
2. **Redo Log File**：磁盘文件（固定大小，循环写入，如 `ib_logfile0/1`）。

#### 执行流程（事务提交）：

1. 事务开始，修改内存中的数据页（产生 **脏页**）；
2. 把修改记录写入 **Redo Log Buffer**；
3. **事务提交时**，强制将 Redo Log Buffer 刷入 **磁盘日志文件**（刷盘策略由 `innodb_flush_log_at_trx_commit` 控制）；
4. 后台线程异步将内存脏页刷入磁盘数据文件（`.ibd`）；
5. 事务正式完成。

#### 关键特性：循环写

Redo Log 是 **固定大小的环形文件**，写满后会从头覆盖旧日志（前提：旧日志对应的脏页已刷入磁盘），避免日志无限膨胀。

### 4. 崩溃恢复原理

MySQL 异常宕机后重启：

1. InnoDB 检查 Redo Log 的日志序列号（LSN）；
2. 对比「内存脏页的 LSN」和「日志文件的 LSN」；
3. 把 **已提交但未刷入磁盘** 的修改，通过 Redo Log 全部重做。

------

## 二、Undo Log

（回滚日志）

### 1. 核心作用

**记录「数据修改前的旧版本」**，两大核心用途：

1. **事务回滚（ROLLBACK）**：事务执行失败 / 手动回滚时，用旧版本恢复数据，保证「事务要么全做，要么全不做」；
2. **MVCC（多版本并发控制）**：实现无锁读，让读操作不阻塞写操作、写操作不阻塞读操作。

### 2. 核心原理

**逻辑日志，而非物理日志**：

- Redo Log 记录「物理修改」（比如在哪个数据页改了什么）；
- Undo Log 只记录「逻辑旧值」：
  - `INSERT` → 记录删除主键；
  - `DELETE` → 记录插入数据；
  - `UPDATE` → 记录修改前的旧值。

### 3. 完整工作机制

#### 存储位置

不单独存文件，存储在 **InnoDB 共享表空间（ibdata1）** 中。

#### 执行流程：

1. 事务修改数据 **前**，先把 **旧版本** 写入 Undo Log；
2. 再执行数据修改操作；
3. 若 **事务回滚**：`**直接读取 Undo Log 的旧版本，恢复数据**`；
4. 若 **事务提交**：Undo Log 不会立即删除（因为其他事务可能需要用旧版本做 MVCC 读），由后台 **Purge 线程** 异步清理。

#### MVCC 核心支撑

可重复读、读已提交隔离级别，本质就是通过 Undo Log 的 **版本链**，让查询读取历史版本数据，无需加锁。

------

## 三、Redo Log vs Undo Log 核心区别

|   维度   |        Redo Log（重做日志）         |       Undo Log（回滚日志）        |
| :------: | :---------------------------------: | :-------------------------------: |
| 核心作用 | 保障 **持久性**，崩溃恢复已提交事务 |   保障 **原子性**，回滚 + MVCC    |
| 记录内容 |  数据 **修改后的新值**（物理日志）  | 数据 **修改前的旧值**（逻辑日志） |
| 写入时机 |       事务执行中、提交时刷盘        |       数据修改 **前** 写入        |
| 存储方式 |    磁盘固定文件，**循环覆盖写**     |    共享表空间，提交后异步删除     |
| 解决问题 |             宕机丢数据              |      事务失败、并发读写冲突       |

------

## 四、两者协同工作

一个事务的完整日志流程：

1. 修改数据前 → 写 **Undo Log**（记录旧版本）；
2. 修改内存数据 → 写 **Redo Log Buffer**（记录新版本）；
3. 事务提交 → 刷 **Redo Log** 到磁盘；
4. 事务成功：Purge 线程后续清理 Undo Log；
5. 宕机重启：
   - 用 Redo Log 重做 **已提交** 事务；包含所有修改记录，都会被重做
   - 用 Undo Log 回滚 **未提交** 事务。上一步重做 RedoLog 的时候，那些没用提交的事务，事务可能只执行了一部分，修改了一部分的数据，这些被修改的数据，不应该被修改，因为整个事务并没有完成。所以需要通过 UndoLog 回滚这些修改的数据。

## 总结

1. **Redo Log** 是「**备忘录**」：记下来已经提交的修改，断电后照着重做，保证数据不丢；
2. **Undo Log** 是「**撤销键**」：记下来修改前的样子，回滚时恢复，同时支撑多版本无锁读；
3. 二者是 InnoDB 事务的基石，缺一不可。

# 如何判断事务已提交但未刷新到磁盘？

通过日志中的 `LSN`、内存数据页的 `LSN` 已经磁盘上数据文件的 `LSN`（日志序列号，InnoDB 内部的全局唯一、永远只增不减的「版本号 / 时间戳」）

##  三个地方都存 LSN

1. Redo Log 文件（磁盘）

   记录：当前 Redo Log 已经写到了哪个 LSN。

2. 内存里的数据页（Buffer Pool）

   数据被修改后，这个页的 LSN 会更新成最新值。

3. 磁盘上的真实数据文件（.ibd）

   当内存脏页真正刷进磁盘时，磁盘数据页的 LSN 才会被更新

## 判断条件

对比 LSN 大小：

如果 **Redo Log 里的 LSN ＞ 磁盘数据页的 LSN**

就说明：这部分修改已经提交，但还没刷到磁盘数据文件。

为什么？

因为 InnoDB 严格遵守 <span style="color:#FF0000;">**WAL（先写日志，再写数据）**</span> 规则：

1. 你执行一个更新事务
2. 先改 **内存数据** → 内存页 LSN 变大
3. 再写 **Redo Log** → Redo LSN 同步变大
4. **事务提交时，必须把 Redo Log 刷到磁盘**（提交成功的标志）
5. 而 **真正把数据刷进 .ibd 文件**，是后台慢慢异步做的，很慢、很滞后

所以：

- **事务提交成功 = Redo Log 已落盘，Redo LSN 已更新**
- **数据落盘 = 磁盘数据页 LSN 追上 Redo LSN**

只要两者不等，就一定存在「已提交未刷盘」的修改。

## 恢复原理

MySQL 突然宕机重启后，InnoDB 做两件事：

**1. 重做阶段：用 Redo Log 把所有修改恢复回来**，包含已经提交事务的修改和未提交事务的修改。未提交的事务中做的修改，可能会被异步线程已经刷新到磁盘了。

**2. 回滚阶段：用 Undo Log 删掉未提交的事务**

## 阶段 1：重做（Redo）

—— 把 “提交过的修改” 找回来

1. InnoDB 先看一个叫 

   Checkpoint（检查点）的位置

   Checkpoint LSN 表示：这个数字之前的所有数据，都已经安全刷进磁盘了，不用管。

2. 从 Checkpoint LSN 开始，往后遍历 Redo Log

3. 把 Redo Log 里记录的所有物理修改，

   重新应用一遍到内存

   → 这一步不管事务有没有提交，先全部恢复

这一步做完：

内存里已经有了 **所有最近的修改**，包括：

- 已提交的
- 还没提交的

## 阶段 2：回滚（Undo）

—— 把 “没提交的” 扔掉

1. InnoDB 去查事务系统表，看哪些事务：
   - 有 `BEGIN`
   - 但 **没有 COMMIT 记录**
2. 对这些未提交事务，用 Undo Log 把数据改回旧版本
3. 已提交的事务，直接保留

# Drop、Truncate、Delete 的区别

## Delete

从表中删除一行或多行的记录

**日志**：每一行被删除的操作都会记录在日志中，可以用来回滚 Call Back。日志量比较大。

**触发器**：会触发定义在表上的 BEFORE DELETE 和 AFTER DELETE 触发器

**标识列**：会不重置自增标识

**空间**：不会立即释放数据页所占用的磁盘空间，后续的 INSERT/UPDATE 可以覆盖这些空间

**锁**：根据 WHERE 条件和数据库实现，可能获得 **行级锁或页级锁**，影响并发性能。

## Truncate

一次性删除表中所有数据

**日志**：只记录整个数据页的释放操作，而不是逐行记录。日志量较小

**触发器**：不会触发 DELETE 触发器

**标识列**：会重置自增标识

**空间**：立即释放数据所占用的磁盘空间

**锁**：需要表级锁，删除时间独占表，阻塞其他操作。

删除速度快，不支持回滚

## Drop

删除整个表结构和全部数据，以及相关联的索引、触发器、索引、约束以及相关的权限设置。

**日志**：记录删除表的操作

**触发器**：不会触发

**标识列**：不存在，也没有必要重置了

**空间**：立即释放数据所占用的数据页，并归还操作系统

**锁**：需要表级锁

# 事务机制

事务是一组数据库操作的逻辑单元，这些操作只能全部成功，或者全部失败回滚。

保证数据库从一个一致性的状态转换到另一个一致性的状态。

## 原子性A

事务被视为一个不可分割的最小工作单元

通过 Undo log 回滚数据

## 一致性C

事务执行的结果必须使数据库从一个一致性状态转换到另一个一致性状态。

一致性主要依赖于应用层的业务逻辑和数据库的完整性约束

## 隔离性I

多个并发执行的事务之间应该相互隔离，使每个事务感觉不到其他事务在同时执行，防止并发事务操作相同数据时导致的数据不一致问题。

主要通过 <span style="color:#990000;">**锁（排他锁）机制和 MVVC 多版本并发控制** </span>实现。

## 持久性D

事务一旦提交，对数据库所作的修改就是永久性的。即使发生崩溃、断电等故障，提交的结果也不会丢失。

主要通过 Redo Log 和持久化存储。

# MVCC

**MVCC**（Multi-Version Concurrency Control，多版本并发控制）是 MySQL InnoDB 存储引擎实现高并发事务处理的核心机制，其核心思想是 <span style="color:#00CC00;">**写不阻塞读，读不阻塞写**，通过维护数据的多个版本，让读操作读取 "过去的版本" 而非最新版本，从而避免读写冲突</span>，大幅提升数据库并发性能。

MVCC 主要用于 **快照读**（普通 SELECT 操作，无需加锁），而 **当前读**（如 SELECT ... FOR UPDATE、UPDATE、DELETE 等）仍需使用锁机制。

## MVCC 实现的核心组件

### 1. 行记录隐藏字段

InnoDB 为每行记录添加了三个隐藏字段，用于实现版本控制：

|    隐藏字段     |  大小  |                             作用                             |
| :-------------: | :----: | :----------------------------------------------------------: |
|  **DB_TRX_ID**  | 6 字节 | 记录最后一次修改该行数据的事务 ID（事务启动时由系统分配唯一递增编号） |
| **DB_ROLL_PTR** | 7 字节 |  回滚指针，指向该行数据在 undo log 中的历史版本，形成版本链  |
|  **DB_ROW_ID**  | 6 字节 |   隐含的自增行 ID（当表没有主键或唯一非空索引时自动生成）    |

### 2. Undo Log（撤销日志）

Undo Log 是 MVCC 实现的 "历史档案馆"，用于存储数据修改前的旧版本，具有双重职责：

- **事务回滚**：当事务需要回滚时，利用 Undo Log 恢复数据到修改前状态，保证事务原子性
- **版本控制**：为 MVCC 提供历史版本数据，供快照读时使用

Undo Log 分为两种类型：

- **insert undo log**：记录插入操作的旧版本，事务提交后可立即删除
- **update undo log**：记录更新 / 删除操作的旧版本，MVCC 核心依赖，需等待不再被任何事务引用时才会被 Purge 线程清理

### 3. undo log版本链

当事务修改数据时，不会直接覆盖原数据，而是：

1. 将旧版本数据写入 undo log
2. 生成新的数据版本，更新 DB_TRX_ID 为当前事务 ID
3. 更新 DB_ROLL_PTR 指向 undo log 中的旧版本
4. 多个版本通过 DB_ROLL_PTR 串联形成 **版本链**，最新版本在数据表中，历史版本在 undo log 中

###  4.Read View

**Read View** 是事务执行<span style="color:#FF0000;">**快照读**</span>时生成的一致性视图，用于判断数据行的哪个版本对当前事务可见。它包含四个关键信息。

关于什么是快照读：

------

#### 当前读

读取的记录时**最新版本，读取时还要保证其他并发事务不能修改当前记录**，会对读取的记录进行加锁。如：

select ... lock in share mode,select ... for update,update,insert,delete(排他锁)都是一种当前读。

#### 快照读

简单的select，不加锁，就是快照读

快照读，读取的是记录数据的可见版本，有可能是历史数据，不加锁，非阻塞读

- Read Committed：每次select都生成一个快照读
- Repeated Read：开启事务后第一个select语句生成快照读

就像操作之前，给数据拍了一张照片，后续根据这个照片上的数据进行操作。

-----

#### 核心字段

| 信息               | 作用                                               |
| ------------------ | -------------------------------------------------- |
| **m_ids**          | 当前活跃（**未提交**）的事务 ID 集合               |
| **min_trx_id**     | m_ids 中的最小事务 ID                              |
| **max_trx_id**     | 系统即将分配给下一个事务的 ID（当前最大事务 ID+1） |
| **creator_trx_id** | 创建该 ReadView 的事务 ID                          |

##  核心原理：可见性判断规则

当事务执行快照读时，InnoDB 会根据以下规则判断**版本链中哪个版本对当前事务可见**：

1. **如果当前版本的 DB_TRX_ID == creator_trx_id **：事务修改过的数据，对自身可见 
2. **如果当前版本的 DB_TRX_ID < min_trx_id**：修改该版本的事务在当前事务生成 ReadView 前已提交，可见
3. **如果当前版本的 DB_TRX_ID >= max_trx_id**：修改该版本的事务在当前事务生成 ReadView 后才启动，不可见
4. 如果 **min_trx_id ≤ DB_TRX_ID < max_trx_id**：
   - 若 DB_TRX_ID 在 m_ids 中：事务未提交，不可见
   - 若 DB_TRX_ID 不在 m_ids 中：事务已提交，可见

**如果当前版本不可见，则通过 DB_ROLL_PTR 指针回溯到上一个版本，重复上述判断，直到找到可见版本或版本链结束**（返回不存在）。

## <span style="color:#4C9900;">MVCC 与事务隔离级别的关系</span>

ReadView 的生成时机决定了事务隔离级别，这是 MVCC 实现不同隔离级别的关键：

| 隔离级别             | ReadView 生成时机                               | 特点                                                         |
| -------------------- | ----------------------------------------------- | ------------------------------------------------------------ |
| **READ COMMITTED**   | 每次执行 SELECT 时生成新的 ReadView             | 每次查询都能看到已提交的最新数据，可能出现不可重复读         |
| **REPEATABLE READ**  | 事务中首次执行 SELECT 时生成 ReadView，后续复用 | 事务中多次查询看到相同数据，避免不可重复读，这是 MySQL 默认隔离级别 |
| **READ UNCOMMITTED** | 不使用 ReadView，直接读取最新版本               | 可能读取未提交数据（脏读），通常不使用                       |
| **SERIALIZABLE**     | 强制使用当前读，通过加锁实现完全串行化          | 最高隔离级别，避免所有并发问题，但性能最低                   |

## 优势与局限

### 优势

1. **高并发性能**：读写不阻塞，大幅提升系统吞吐量
2. **避免锁竞争**：快照读无需加锁，减少死锁风险
3. **一致性视图**：为事务提供一致的数据快照，符合 ACID 特性

### 局限

1. **版本管理开销**：需要维护版本链和 undo log，占用额外存储空间
2. **Purge 线程压力**：需要定期清理不再需要的 undo log 版本
3. **仅适用于 InnoDB**：MyISAM 等其他存储引擎不支持 MVCC

## 总结

MySQL <span style="background:#66FF66;">MVCC 通过 **隐藏字段 + 版本链 + Undo Log+Read View** 四大组件</span>，实现了 "多版本数据管理策略"，核心是<span style="color:#CC0000;">**让每个事务看到自己专属的数据快照，从而在保证事务隔离性的同时，最大化提升数据库并发处理能力**</span>。理解 MVCC 原理对于优化 MySQL 高并发性能和解决事务相关问题至关重要。

# 事务隔离级别

隔离级别定义了多个并发事务之间如果看到彼此未提交或以及提交的数据更改，他解决了数据库并发操作中可能出现的脏读、不可重复度和幻读的问题

## 1.读未提交

事务可以读取其他没用提交事务修改的数据

并发级别最高，隔离级别最低，但也是最不安全的级别

存在<span style="color:#CCCC00;">脏读</span>（A事务看到了其他事务没用提交的数据）、<span style="color:#009900;">不可重复读</span>（A事务中两次查询中，后面的查询和第一次查询的数据不一样，中间被其他事务修改了。数据不一致）、<span style="color:#FF6666;">幻读</span>（两次的结果集数量不一致，同一个事务中后面的查询包含了其他事务新插入的行）的问题

## 2.读已提交

事务只能读取其他已经提交事务修改的数据

解决了脏读，存在不可重复读（A事务慢，中间B事务的修改已经完成）和幻读的问题

## 3.可重复读

确保在同一个事务中多次读取同一范围内的数据时，结果是一致的。（通过快照实现）

默认隔离级别

一个事务执行过程中，其他事务对同一范围内的数据进行了修改操作，这些操作对于该事务是不可见的。

解决了脏读和不可重复读。

在标准的SQL定义中，这个级别可能发生幻读（一个事务重新执行一个查询，返回的结果集包含其他新提交事务插入的行）。

MySQL 的实现特殊性：MySQL的InnoDB存储引|擎通过多版本并发控制 和 间隙锁 机制，在可重复读级别下很大程度上防止了幻读的发生（虽然不是100%绝对避免所有理论上的幻读场景，但在绝大多数实际场景中避免了）。

## 4.序列化

最高的隔离级别。通过强制事务串行执行（而不是并发执行）来避免所有并发问题。

# 分库分表后如果维护id

分库分表后，全局唯一且趋势递增的主键id的设计是一个核心调整

## 1.UUID

实现简单，本地生成，全球唯一性保证非常好

长度过长，作为主键存储空间大，索引效率低。

## 2.数据库自增ID（集中分配）

单独建立一个数据库，用来维护id。每次插入数据库都从这个获取。

效率低

## 3.号段模式

业务系统启动时候或者ID用完的时候，向中心数据库匹配申请一个号段。

中心数据库更新最大值（当前最大值+步长），并返回号段范围（1000-2000）

业务系统在本地内存中使用这个号段，分配完后再去申请新的号段。

存在号段丢失的可能性

中心数据库存在潜在的故障

## 4.Redis生成ID

利用Redis单线程和INCR/INCRBY命令的原子性来生成自增ID

redis单点问题，需要配合redis集群

## 5.雪花算法

使用雪花算法或其变种生成id

缺点：

时钟回拨问题，如果服务器的系统时间发生回退，可能导致生成重复的ID

解决方法：

- 关闭NTP同步，但可能产生时间漂移

- 扩展WorkerID位数，预留一部分ID作为“时间回拨缓冲”，如美团的Leaf-Snowflake

## 选择规则

1. 首选Snowflake及其工业级变种（Leaf-Snowflake，UidGenerator）
2. 号段模式
3. ID生成服务
4. UUID

# 分库分表

## 什么时候需要分库分表

磁盘io太大，网络请求太大，单表数据过多

### 水平分库

系统并发量很大，分表难以解决问题

### 水平分表

解决单表数据量很大的问题，影响sql效率，加重cpu负担的时候

### 垂直分库

以表为依据，按照业务归属不同，将不同的表拆分到不同的库中

比如，微服务中，不同的服务拥有各自独属的数据库

### 垂直分表

以字段为依据，按照字段的活跃性，将表中不同的字段拆分到不同的表中。

类似数据库设计范式，将表的冗余性降低，将不常用的字段单独作为一张表，和原表做关联。

## 常用工具

### sharding-jdbc

属于client层的方案，不用部署，运维成本低，不需要代理层的二次转发请求，性能很高，但是各个系统都需要耦合Sharding-jdbc的依赖，升级比较麻烦

### mycat

属于Proxy层方案，需要部署，自己运维一层中间件，运维成本高。

## 常见问题

### 如果模糊查询呢？

### 方案 1：强制业务携带「分片键精确值」

（✅ 最优、零成本）

**适用**：90% 的业务场景（如用户中心、订单系统）。

**核心思路**：模糊查询必须让前端 / 业务方传入**分片键精确值**（如用户 ID、订单 ID），从根源实现精准路由。

**优点**：性能极致、无架构改造、无数据冗余、开发成本最低。

**例子**：查自己的昵称模糊 → 前端必传 `user_id`；查订单备注模糊 → 必传 `order_id`。

------

### 方案 2：广播查询（全库扫描）

（⚠️ 仅低频次、小数据量）

**适用**：后台管理系统、低频查询、数据量小的场景。

**原理**：分库分表中间件（Sharding-JDBC、MyCat）自动将 SQL 广播到所有 8 个库 / 表，并行执行后聚合结果。

**优点**：无需改造业务，开箱即用。

**缺点**：高并发 / 大数据量下会压垮数据库（雪崩风险），**禁止用于 C 端接口**。

**中间件自动处理**：你不用手动写 8 个库的查询代码，框架自动完成。

------

### 方案 3：引入搜索引擎（ES/Solr）

（🏆 工业级标准方案）

**适用**：C 端高频、多条件模糊、非分片键查询（终极解决方案）。

**核心思路**：<span style="color:#009900;">**双写数据 + 先查 ES 再查分库**</span>

1. 数据写入：分库分表存核心业务数据，**同步冗余一份到 ES**（存储所有模糊查询字段 + 分片键）；

2. 查询流程：

   - 第一步：ES 做**高性能模糊 / 多条件模糊查询**，得到符合条件的**分片键精确值列表**；

   - 第二步：用分片键列表**取模路由**到对应库表，查询完整数据；

   - 第三步：聚合结果返回。

     优点：解决所有模糊查询痛点，性能百万级 QPS 无压力。

     例子：电商按「商品名称 + 类目 + 价格」多条件模糊查询 → ES 查商品 ID → 分表查详情。

------

### 方案 4：冗余全局表

（✅ 小表、高频模糊专用）

**适用**：数据量小、需要频繁模糊查询的表（如用户基础信息、字典表）。

**核心思路**：把需要模糊查询的字段，**冗余一份到单库单表的全局表**（不拆分）。

- 模糊查询：直接查全局表，得到分片键；

- 详情查询：用分片键路由到分库分表。

  缺点：数据冗余，需要保证双写一致性（用事务 / 消息队列）。

------

### 方案 5：替换分片算法

（兜底方案）

**取模分片天生不支持模糊 / 范围查询**，如果无法接受以上方案，可以替换分片规则：

1. **范围分片**：`user_id 1-10000` → 表 1，`10001-20000` → 表 2（支持前缀模糊，但有数据倾斜）；

2. 一致性哈希：仅解决扩容问题，不解决模糊查询。

   结论：不如 ES 方案通用，不推荐。

------

# 索引B+树

[B树和B+树的插入、删除图文详解-阿里云开发者社区](https://developer.aliyun.com/article/1537051)

## B+树长什么样子

InnoDB 里的 B+ 树有几个**铁律**：

1. 它是**多路平衡查找树**，不是二叉的；

2. 整棵树按 ** 页（Page）** 组织，默认一页 16KB；

3. 分为两层节点：

   - **非叶子节点（索引页）**：只存「索引键 + 子节点指针」，**不存真实数据**
   - **叶子节点（数据页）**：存**所有索引键 + 完整行数据**（聚簇索引），并且**用双向链表串起来**

   

4. 所有查询最终都必须走到**叶子节点**才能拿到数据。

## 怎么索引的

### 1. 主键索引（聚簇索引）

- 根节点、中间节点：只存**主键值 + 下一层页指针**
- 叶子节点：直接存**一整行完整数据**

**查找过程：**

比如查 `id = 1000`

1. 加载**根节点页**到内存，比较 1000 落在哪个区间；
2. 根据指针加载下一层**中间节点页**；
3. 重复直到定位到**叶子节点页**；
4. 直接在该页里取出整行数据。

整个过程只需要**很少几次磁盘 IO**。

### 2. 普通索引（二级索引）

- 整棵树依然是 B+ 树
- 叶子节点：存的是**索引列值 + 主键 ID**，不存整行数据

**查找过程（回表）：**

比如查 `name = '张三'`

1. 走 name 索引的 B+ 树，找到叶子节点，拿到对应的主键 id；
2. 再拿着 id 去**主键索引树**查一遍，拿到完整数据。

这就是**回表**

## 为什么 MySQL 非要用 B+ 树？

为了**尽量少读磁盘**，同时让**范围查询、排序、分页**变得极快，完美适配 MySQL 这种磁盘型数据库。

### 淘汰二叉树

数据有序时会**退化成链表**；

层级极深，磁盘 IO 爆炸；

直接 PASS。

### 淘汰红黑树

红黑树是平衡二叉树，层级依然很高。

假设 1000w 数据，高度大约在 20 多层。

每一层都可能一次磁盘 IO，**太慢了**。

数据库瓶颈从来不是 CPU，是**磁盘 IO**

### 淘汰B树

B 树和 B+ 树很像，但有一个致命区别：

- B 树：**每个节点都存数据**
- B+ 树：只有叶子节点存数据，非叶子只存索引键

结果：

- B 树一页能存的**索引数量少**，树更高，IO 更多；
- B 树**不支持链表式范围查询**，区间查询要频繁回溯；
- 同一 SQL，B 树的 IO 次数通常远多于 B+ 树。

# 常见的索引原则

索引的设计是sql优化的核心

## 高频查询优先

针对where，join，order by和group by字句中的列建立索引

## 高选择性列优先

区分度高的列

区分度=`select count(distinct col)/count(*) from table`

## 最左前缀匹配原则

联合索引（a,b,c）生效场景：

where a=1

where a=1 and b=2

但是where b=2不生效

## 优化策略

1. 覆盖索引
2. 索引下推
3. 前缀索引

## 避坑

### 避免冗余索引

 联合索引（a，b）已经存在的情况下，再建立a索引是冗余的，但是（b，a）不冗余

### 谨慎使用表达式

`where year（create_time）= 2026`会导致索引失效

`where create_time between '2026-01-01' and '2026-12-31'`索引可以正常使用

### 索引与排序优化

`order by`所使用的列应该尽量和索引/联合索引的顺序一致

在顺序一致的情况下，可以避免filesort

比如联合索引（a,b,c）

索引可用时支持`order by a,b,c` 

### 控制索引数量

单表索引数量不超过5个

写操作的时候维护索引成本高

# 什么是表空间？什么作用？

## 一、表空间是什么

在 MySQL 中，**表空间（Tablespace）** 是 InnoDB 存储引擎特有的<span style="color:#CC0000;">**逻辑存储容器**</span>，位于数据库与物理磁盘文件之间，用于组织和管理表数据、索引、事务日志等核心数据对象。它是 InnoDB 逻辑存储结构的最高层，将物理文件（如`.ibd`、`ibdata1`）抽象为统一的管理单元，实现数据的高效存储与访问。

**关键特性**：

- 表空间由一个或多个物理数据文件组成（通常是`.ibd`或`ibdataX`格式）
- 内部采用**段（Segment）→区（Extent）→页（Page）→行（Row）** 的分层结构管理数据
- 仅适用于 InnoDB 引擎，MyISAM 等其他引擎不支持此概念

## 二、表空间的核心类型与功能

MySQL InnoDB 提供 5 种核心表空间类型，各有特定用途与适用场景：

### 1. 系统表空间（System Tablespace）

**默认文件**：`ibdata1`（默认初始大小 12MB，自动扩展）

**核心作用**：

- 存储 InnoDB 数据字典（表结构定义）、双写缓冲区、插入缓冲区、回滚段（MySQL 5.7 前）等核心元数据
- 未启用独立表空间时，存储所有用户表数据和索引
- 记录事务系统信息，保障数据库崩溃恢复能力

### 2. 独立表空间（File-Per-Table Tablespaces）

**默认文件**：`tablename.ibd`（每张表对应一个独立文件）

**核心作用**：

- MySQL 5.6 + 默认启用（通过`innodb_file_per_table=ON`控制）
- 实现单表数据与索引的物理隔离，便于单表备份 / 还原 / 迁移
- **表删除后可直接释放磁盘空间**，避免系统表空间膨胀问题
- 支持 TRIM/DISCARD 操作，优化 SSD 存储性能
  - 通过独立表的表空间文件，<span style="color:#CC0000;">**.idb和.cfg文件可以移动大表数据**</span>
  - 步骤：
    - 在源服务器上解锁表 unlock tables；
    - 在模板服务器上创建相同的表结构
    - 丢弃目标服务器上空表的表空间：`ALTER TABLE table——name DISCARD TABLESPACE ;`
    - 将复制的.idb和.cfg文件放入目标库的正确位置，并设置正确的权限
    - 导入表空间`ALTER TABLE table-name IMPORT TABLESPACE`
    - 这比mysqldump要快

### 3. 通用表空间（General Tablespaces）

**MySQL 5.7 + 引入**，用户可手动创建的共享表空间

**核心作用**：

- 允许多张表共享同一`.ibd`文件，平衡独立表空间与系统表空间的优缺点

- 支持将表分配到指定表空间，实现 I/O 隔离与资源管控

- 减少小表碎片化，提升存储利用率

- 语法示例：

  ```sql
  CREATE TABLESPACE `ts_archive` ADD DATAFILE 'ts_archive.ibd' ENGINE=InnoDB;
  CREATE TABLE orders (id INT) TABLESPACE `ts_archive`;
  ```

### 4. 回滚表空间（Undo Tablespaces）

**默认文件**：`undo_001`、`undo_002`（MySQL 5.7 + 默认独立，之前存储在系统表空间）

**核心作用**：

- 存储 Undo Log（撤销日志），用于事务回滚和 MVCC 多版本并发控制
- 支持事务 ACID 特性中的原子性（Atomicity）与隔离性（Isolation）
- 可通过`innodb_undo_directory`指定存储路径，实现 I/O 隔离

### 5. 临时表空间（Temporary Tablespaces）

**默认文件**：`ibtmp1`（会话临时表空间）与`temp_%d.ibd`（全局临时表空间）

**核心作用**：

- 存储用户创建的临时表和数据库内部生成的临时表（如排序、分组操作）
- 会话结束或数据库重启时自动清理，避免磁盘空间占用
- 支持大临时表操作，提升查询性能

## 三、表空间的核心作用

|   作用类别   |                           具体说明                           |
| :----------: | :----------------------------------------------------------: |
| **数据组织** | 作为逻辑容器，统一管理表数据、索引、元数据，屏蔽底层物理存储差异 |
| **并发控制** |  配合 MVCC 机制，通过回滚表空间存储历史版本，实现读写不阻塞  |
| **崩溃恢复** |   系统表空间记录关键恢复信息，保障数据库故障后的数据一致性   |
| **性能优化** | 支持 I/O 隔离（通用表空间）、碎片管理（独立表空间）、SSD 优化（TRIM）等性能特性 |
| **存储管理** |     灵活控制数据存储位置，支持跨磁盘扩展，提升存储利用率     |
| **备份恢复** | 独立表空间简化单表备份，通用表空间便于批量管理，提升运维效率 |

## 四、表空间的内部结构

表空间采用分层结构高效管理数据，核心层级如下：

1. **段（Segment）**：对应索引（主键索引 + 二级索引），每个索引包含叶子节点段和非叶子节点段
2. **区（Extent）**：64 个连续页（默认 16KB 页，即 1MB），是 InnoDB 磁盘分配的基本单位MySQL
3. **页（Page）**：InnoDB 最小 I/O 单元（默认 16KB），存储行数据、索引数据、undo 日志等MySQL
4. **行（Row）**：数据存储的最小逻辑单位，包含用户定义列和 3 个隐藏字段（DB_TRX_ID、DB_ROLL_PTR、DB_ROW_ID）

## 五、表空间管理的关键配置与操作

### 1. 常用配置参数

|             参数             |        作用        |          默认值          |
| :--------------------------: | :----------------: | :----------------------: |
|   `innodb_file_per_table`    |   启用独立表空间   |     ON（MySQL 5.6+）     |
|   `innodb_data_file_path`    | 系统表空间文件配置 | `ibdata1:12M:autoextend` |
|  `innodb_undo_tablespaces`   |   回滚表空间数量   |            2             |
| `innodb_temp_data_file_path` |   临时表空间配置   | `ibtmp1:12M:autoextend`  |

### 2. 常用操作命令

```sql
-- 查看表空间配置
SHOW VARIABLES LIKE 'innodb_file_per_table';
SHOW VARIABLES LIKE 'innodb_data_file_path';

-- 创建通用表空间
CREATE TABLESPACE `ts_archive` ADD DATAFILE 'ts_archive.ibd' ENGINE=InnoDB;

-- 移动表到指定表空间
ALTER TABLE orders TABLESPACE `ts_archive`;

-- 释放表空间碎片（独立表空间）
ALTER TABLE orders FORCE;
ALTER TABLE orders DISCARD TABLESPACE;
ALTER TABLE orders IMPORT TABLESPACE;
```

## 总结

表空间是 MySQL InnoDB 存储引擎的核心存储管理机制，通过**<span style="color:#00CC00;">逻辑容器抽象物理存储，实现数据的高效组织、并发控制与存储管理</span>**。理解表空间类型与作用，对于数据库性能优化、存储规划、备份恢复等运维工作至关重要。实际应用中，建议默认使用独立表空间，结合通用表空间管理小表，通过回滚表空间优化并发性能，构建高效稳定的 InnoDB 存储环境。

# 如何优化ORDER BY查询？

核心就是避免文件排序（FileSort），利用索引直接返回有效数据

## 1.覆盖索引

<span style="color:#CC0000;">覆盖索引</span>：查询使用了索引，并且返回的列，都属于索引列。

直接利用复合索引，使mysql直接从索引中返回有序数据

在索引中包含ORDER BY的列

```sql
-- 原始查询 需要排序

select order_id,score from `order` order by order_id ,socre

-- 添加复合索引
ALTER TABLE `order` ADD INDEX idx_socre(order_id,score)
```

## 2.where + ORDER BY联合优化

创建包含where条件和order by列的复合索引

where order_id = 100 order by score

idx_id_score(order_id,score)

## 3.使用limit减少排序量

可提前终止排序

## 4.避免排序字段计算

索引不存储计算值，对列使用函数或计算会导致索引失效

## 5.调正排序缓冲区大小

`set session sort_buffer_size = 4 * 1024 * 10254 --4MB`

## 6.<span style="color:#CC0000;">处理大偏移分页</span>

延迟关联（Delayed Join）,是 MySQL 大偏移分页的**标准优化方案**

优化的核心：**<span style="color:#00CC00;">先用索引完成排序和分页，只拿到主键，再通过主键回表查完整数据。覆盖索引+子查询</span>**

### 示例

```sql
-- id有索引 price是二级索引
-- 低效
select * from products 
order by price
limit 10000,20

-- 高效
select * from products
join (
	select id from products
    order by price
    limit 10000,20
) as tmp using(id) 
-- using(id) 相当于 on tmp.id = products.id 的简写
```

### 解析

#### 低效sql

它的执行步骤是：

1. **全量扫描 / 索引扫描**：MySQL 需要找到所有数据，按 `price` 排序；
2. **暴力跳过大量数据**：为了取第 10001~10020 行，**必须先读取并丢弃前 10000 行**；
3. **读取整行所有字段**：每一行都要读取 `*` 代表的**全部列数据**（而不只是排序需要的 `price` 和主键 `id`）；
4. **高 IO 消耗**：读取了大量无用的整行数据，磁盘 IO 和内存占用极高。

##### 核心痛点：

大偏移分页（`limit 10000,20`）最坑的不是取 20 行，而是**要先扫描 + 丢弃前 10000 行的完整数据**，这是性能杀手。

#### 高效sql

##### 第一步：只查「主键

子查询只查「主键 id」

```sql
select id from products order by price limit 10000,20
```

1. 极致利用索引（覆盖索引）：
   - 如果 `price` 有**二级索引**：InnoDB 的二级索引叶子节点，本身就存储了**主键 id**。这个子查询**只需要查索引**，不需要访问真实数据行（专业名：**Using index 覆盖索引**），速度极快；
   - 哪怕 `price` 无索引：也只需要读取 `id` 这一列，数据量远小于读取所有列。
2. **排序成本极低**：排序的对象是 `id+price`（极小的索引数据），而不是整行数据；
3. **只获取 20 个 id**：最终只得到需要的 20 个主键 ID，没有任何冗余数据。

##### 第二步：精准查询

通过主键「精准查询」完整数据

```sql
主表 join 子查询结果 using(id)
```

- `id` 是**主键聚簇索引**，通过主键查询是**最快的查询方式**（O (1) 复杂度）；
- 只需要**精准读取 2 行数据**，完全不扫描无用数据，磁盘 IO 几乎可以忽略

```sql
主表 join 子查询结果 using(id)
```

- `id` 是**主键聚簇索引**，通过主键查询是**最快的查询方式**（O (1) 复杂度）；
- 只需要**精准读取 20 行数据**，完全不扫描无用数据，磁盘 IO 几乎可以忽略。

# Filesort

[一篇文章彻底搞懂MySql之order by索引优化、文件排序原理（进阶篇）_order by 索引-CSDN博客](https://blog.csdn.net/qq_33522097/article/details/127695024)

在 MySQL 中，文件排序（filesort）是指当查询结果需要排序但无法使用索引排序时，MySQL 会使用外部排序来完成。这种排序方式通常会在 *EXPLAIN* 关键字的 *Extra* 列中显示为 *Using filesort*。

## 单路排序和双路排序

文件排序主要分为两种方式：**单路排序**和**双路排序**。

### 单路排序

单路排序的过程如下：

1. 从索引中找到第一个满足条件的主键 ID。
2. 根据主键 ID 取出整行数据，并将所有字段的值存入排序缓冲区（sort buffer）。
3. 重复上述步骤，直到不再满足条件。
4. 对排序缓冲区中的数据按照指定字段进行排序。
5. 返回排序后的结果给客户端。

例如：

`EXPLAIN SELECT * FROM employees WHERE name = 'LiLei' ORDER BY position;`

在这个查询中，MySQL 会一次性取出满足条件的所有字段，然后在排序缓冲区中进行排序。

### 双路排序

双路排序的过程如下：

1. 从索引中找到第一个满足条件的主键 ID。
2. 根据主键 ID 取出整行数据，并将排序字段和主键 ID 存入排序缓冲区。
3. 重复上述步骤，直到不再满足条件。
4. 对排序缓冲区中的数据按照排序字段进行排序。
5. 根据排序后的主键 ID 回表取出所有字段的值，并返回给客户端。

例如：

`EXPLAIN SELECT * FROM employees WHERE name = 'LiLei' ORDER BY position;`

在这个查询中，MySQL 会先取出排序字段和主键 ID，然后进行排序，最后根据排序后的主键 ID 回表取出所有字段。

## 文件排序内存不足的处理

当排序缓冲区（sort buffer）不足以容纳所有数据时，MySQL 会使用临时磁盘文件进行排序。这种情况下，*number_of_tmp_files* 参数会显示使用的临时文件数量。

## 使用哪种排序方式

MySQL 通过比较系统变量 `max_length_for_sort_data`（默认 1024 字节）的大小和需要查询的字段总大小来判断使用哪种排序模式：

如果字段的总长度小于 `max_length_for_sort_data`，则使用单路排序。如果字段的总长度大于 *max_length_for_sort_data*，则使用双路排序。

## using index 和 using filesort 的区别

**using index**：使用二级索引树进行排序，效率较高。

**using filesort**：使用主键索引进行排序，效率较低。

由于 using filesort 需要加载整张表的数据，而 using index 只需要加载二级索引的数据，因此 using index 的效率更高。

# 一级索引和二级索引

主键索引是「一级 / 主索引」，除此之外建的所有普通索引，都叫「二级索引 / 辅助索引」

## 一级索引

整张表的数据，本身就是按主键 id 组织成一棵 B+ 树

这棵树就叫：

- **聚簇索引**
- **主键索引**
- 也可以叫 **一级索引**

它的特点：

- 叶子节点 = **完整的一行数据**
- 你通过 id 查询，直接就能拿到整行数据，不需要再查别的地方

所以它是**最底层、最核心**的索引结构，叫「一级」。

## 二级索引

idx_colume_name(colume)

它是**另外单独建的一棵 B+ 树**，结构是：

```sql
叶子节点：(colume 值, 主键 id)
```

关键点：

- 它**不存完整行数据**
- 想拿到完整数据，必须先用这个索引找到 id，再去 **主键索引（一级索引** 里查
- 它是**依附、辅助**主键索引来工作的



# Binlog

## 1 核心作用

binlog（二进制日志）是MySQL 服务器层的日志（所有存储引擎都支持，包括MyISAM和InnoDB），核心作用有两个：

1. **数据恢复**：<span style="color:#FF0000;">通过binlog 可以恢复指定时间点的数据，比如误删表、误更新数据后，能通过binlog 回放操作，恢复数据（弥补redo log 只能恢复未刷盘数据的不足）</span>。
2. **主从同步**：主库将binlog 发送给从库，从库通过回放binlog 中的操作，保持主从数据一致，这是MySQL 主从架构的核心基础。

和redo log 相比，binlog 有两个关键区别：

- 范围不同：binlog 是服务器层日志，所有存储引擎都支持；redo log 是InnoDB 引擎特有。
- 内容不同：binlog 记录的是“完整的SQL操作”（或数据行的变更），是“逻辑日志”；redo log 记录的是“数据修改的动作”，是“物理日志”（针对InnoDB 数据页）。
- 写入时机不同：binlog 只在事务提交时写入；redo log 在事务执行过程中就会写入。

## 2 核心特性：追加写+不循环

binlog 采用“追加写”的方式，不会循环覆盖，当一个binlog 文件写满（默认大小1G，可通过参数配置），会自动创建一个新的binlog 文件，文件名按“mysql-bin.000001、mysql-bin.000002”的顺序递增。

这种设计的优势是：可以完整保留所有数据变更记录，便于数据恢复和主从同步，即使某个binlog 文件损坏，也不会影响其他文件的内容。

- 通过索引对数据进行排序，降低数据排序的成本，降低cpu消耗

## 优势

1. 查找时磁盘 I/O 次数更少，因为 B+树的非叶子结点可以存储更多的关键字，数据量相同的情况下，B+树更加 “矮胖” ，效率更高。
2. B+树查询所有关键字的磁盘 I/O 次数都一样，查询效率稳定。
3. B+树进行**区间查找**时更加简便实用。

# 索引创建原则

- 数据量大，查询比较频繁的表
- 常作为查询，排序，分组操作的字段
- 字段内容区分度高
- 尽量建立联合索引
- 控制索引数量

# 索引失效场景

- 违反最左前缀法则
  - 索引多列的时候，不能跳过索引的列，要按照索引的最左列开始
  - （a,b,c）索引，查询的时候使用了（a,b,c）则都生效
  - 如果是（a,c）被使用，那么只有a索引生效
  - 如果不带a，则全部失效
- 组合索引中，进行了范围查询的列，其后面的索引列索引会失效
  - 假如还是（a，b，c），但是进行了where a = 1 and b>1 and c =2，这个时候c索引失效
- 索引列进行运算操作
- 索引列隐式类型转换
- 对索引列进行左模糊查询
- 进行or查询时，包含了索引列和非索引列
