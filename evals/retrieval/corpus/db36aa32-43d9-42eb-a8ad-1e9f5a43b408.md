# 单点登录

SSO：SSO 英文全称 Single Sign On，单点登录。SSO 是在多个应用系统中，用户只需要登录一次就可以访问所有相互信任的应用系统。

## 优点

1. **用户角度** :用户能够做到一次登录多次使用，无需记录多套用户名和密码，省心。
2. **系统管理员角度** : 管理员只需维护好一个统一的账号中心就可以了，方便。
3. **新系统开发角度:** 新系统开发时只需直接对接统一的账号中心即可，简化开发流程，省时。

## 核心应用

| 应用/模块/对象    | 说明                                |
| ----------------- | ----------------------------------- |
| 前台站点          | 需要登录的站点                      |
| SSO 站点-登录     | 提供登录的页面                      |
| SSO 站点-登出     | 提供注销登录的入口                  |
| SSO 服务-登录     | 提供登录服务                        |
| SSO 服务-登录状态 | 提供登录状态校验/登录信息查询的服务 |
| SSO 服务-登出     | 提供用户注销登录的服务              |
| 数据库            | 存储用户账户信息                    |
| 缓存              | 存储用户的登录信息，通常使用 Redis  |

## 登录服务

```java
/**
     * 登录验证
     *
     * @param username 用户名
     * @param password 密码
     * @param code     验证码
     * @param uuid     唯一标识
     * @param cid      手机标识符
     * @return 结果
     */
public String login(String username, String password, String code, String uuid, String type, String cid) {
    // 登录前置校验
    loginPreCheck(username, password);
    // 用户验证
    Authentication authentication = null;
    try {
        UsernamePasswordAuthenticationToken authenticationToken = new UsernamePasswordAuthenticationToken(username, password);
        AuthenticationContextHolder.setContext(authenticationToken);
        // 该方法会去调用UserDetailsServiceImpl.loadUserByUsername
        authentication = authenticationManager.authenticate(authenticationToken);
    } catch (Exception e) {
       // 。。。。。。
    } finally {
        AuthenticationContextHolder.clearContext();
    }
   
    LoginUser loginUser = (LoginUser) authentication.getPrincipal();
    recordLoginInfo(loginUser.getUserId());
    // 校验登录用户是否有后台登录权限
    if (StringUtils.isNotEmpty(type) && Objects.equals(type, "web")) {
        int count = userService.checkUserLoginWebAuth(loginUser.getUserId());
        if (count <= 0) {
            throw new ServiceException("您没有后端系统登录权限");
        }
    }
    // 更新 cid
    userService.updateCid(loginUser.getUserId(), cid);
    // 生成token
    return tokenService.createToken(loginUser);
}
```

@Override
public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
    SysUser user = userService.selectUserByUserName(username);
    if (StringUtils.isNull(user)) {
        log.info("登录用户：{} 不存在.", username);
        throw new ServiceException(MessageUtils.message("user.not.exists"));
    } else if (UserStatus.DELETED.getCode().equals(user.getDelFlag())) {
        log.info("登录用户：{} 已被删除.", username);
        throw new ServiceException(MessageUtils.message("user.password.delete"));
    } else if (UserStatus.DISABLE.getCode().equals(user.getStatus())) {
        log.info("登录用户：{} 已被停用.", username);
        throw new ServiceException(MessageUtils.message("user.blocked"));
    }

    passwordService.validate(user);

    return createLoginUser(user);
}

public UserDetails createLoginUser(SysUser user) {
    return new LoginUser(user.getUserId(), user.getDeptId(), user, permissionService.getMenuPermission(user));
}
}

## 密码校验

```java
public void validate(SysUser user) {
    Authentication usernamePasswordAuthenticationToken = AuthenticationContextHolder.getContext();
    //从security提供的上下文中获取用户输入的用户名和密码
    String username = usernamePasswordAuthenticationToken.getName();
    String password = usernamePasswordAuthenticationToken.getCredentials().toString();

    Integer retryCount = redisCache.getCacheObject(getCacheKey(username));

    if (retryCount == null) {
        retryCount = 0;
    }

    if (retryCount >= Integer.valueOf(maxRetryCount).intValue()) {
        AsyncManager.me().execute(AsyncFactory.recordLogininfor(username, Constants.LOGIN_FAIL,
                                                                MessageUtils.message("user.password.retry.limit.exceed", maxRetryCount, lockTime)));
        throw new UserPasswordRetryLimitExceedException(maxRetryCount, lockTime);
    }

    if (!matches(user, password)) {
        retryCount = retryCount + 1;
        AsyncManager.me().execute(AsyncFactory.recordLogininfor(username, Constants.LOGIN_FAIL,
                                                                MessageUtils.message("user.password.retry.limit.count", retryCount)));
        redisCache.setCacheObject(getCacheKey(username), retryCount, lockTime, TimeUnit.MINUTES);
        throw new UserPasswordNotMatchException();
    } else {
        clearLoginRecordCache(username);
    }
}

public boolean matches(SysUser user, String rawPassword) {
    return SecurityUtils.matchesPassword(rawPassword, user.getPassword());
}

public void clearLoginRecordCache(String loginName) {
    if (redisCache.hasKey(getCacheKey(loginName))) {
        redisCache.deleteObject(getCacheKey(loginName));
    }
}
```

# springSecurity是如何进行认证和鉴权的

底层靠**过滤器链**依次拦截请求，走完认证再做权限校验。

## 核心组件速记

1. **SecurityContext**：存放当前登录用户信息
2. **Authentication**：认证主体，用户名、权限、状态
3. **UserDetails**：封装用户账号密码、权限、锁定状态
4. **UserDetailsService**：根据用户名查询数据库用户
5. **PasswordEncoder**：密码加密比对
6. **Authority**：权限标识
7. **FilterSecurityInterceptor**：最终权限拦截校验

## 认证流程（登录校验）

1. 请求进入**过滤器链**，走到登录认证过滤器
2. 封装账号密码为`Authentication`未认证对象
3. 调用`UserDetailsService`根据用户名查库
4. 拿到数据库用户信息`UserDetails`
5. **PasswordEncoder**比对前端密文和库中加密密码
6. 密码一致 → 生成已认证`Authentication`
7. 存入**SecurityContext**上下文，认证完成

------

## 鉴权流程（访问接口权限）

1. 认证通过后，请求走到权限拦截器
2. 读取当前用户携带的**角色 / 权限**
3. 比对当前接口配置的访问权限
4. 权限匹配 → 放行访问接口
5. 权限不足 → 直接返回 403 无权限

------

## 常用授权注解 & 配置

### 1. 注解方式

```java
// 拥有admin权限才可访问
@PreAuthorize("hasAuthority('admin')")
// 拥有管理员角色才可访问
@PreAuthorize("hasRole('ADMIN')")
```

### 2. 代码配置放行 / 拦截

```java
http.authorizeRequests()
    .antMatchers("/login").permitAll() // 匿名放行
    .antMatchers("/admin/**").hasRole("ADMIN")
    .anyRequest().authenticated(); // 其余必须登录
```

## 大分页问题

工单查询业务中，工单数量较多。

项目工单模块数据量持续增长，日常列表分页查询尚可，**页码靠后的大分页查询响应很慢**，越往后翻页耗时越高，前端加载卡顿，影响使用体验。

### 产生原因

MySQL 普通 `limit offset,size` 分页机制，偏移量 offset 越大，数据库需要扫描并丢弃前面大量数据，检索成本急剧升高

工单表数据量大，查询关联字段多，索引覆盖不全，回表查询消耗额外性能

### 解决办法

- sql优化：

  - 放弃传统页码分页，改用**上一页最大 ID 作为查询游标**

  - sql：

    ```sql
    -- 原低效写法
    select * from work_order limit 10000,10;
    
    -- 优化游标写法
    select * from work_order where id > #{lastMaxId} limit 10;
    ```

    利用主键索引有序特性，直接定位起始位置，规避大量数据扫描丢弃，大幅提升深分页速度。

- 索引优化：

  - 针对查询、筛选、排序字段建立联合索引，避免全表扫描
  - 遵循**覆盖索引**原则，查询只取业务必需字段，减少回表次数

## 仓库设施一致性问题

仓库出入库设施的时候，热点设施的一致性问题。

出库的时候需要减少库存，入库则增加库存。

同时出库，导致超出库问题：库存数量 < 真实出库设施数量（redis+lua）

同时入库，导致少入库问题：两个入库，结果数据库库存只增加了一个（不要在业务中增加，使用sql自增，加分布式锁，乐观锁）

### 解答

在仓库管理系统开发中，我负责货品出入库库存模块，遇到**热门货品并发操作引发库存数量不一致**的难题。

困难主要是多请求同时操作同款货品，查询和更新库存非原子执行，出现数据覆盖、超出库、库存负数，同时分布式环境下普通锁失效，一致性和并发性能无法兼顾。

问题根源是库存查询与修改拆分执行，并发读取旧数据互相覆盖，分布式节点无法统一管控操作顺序。

我采用四层方案解决：

第一，数据库更新语句加入库存判断，利用行锁兜底防止负库存；

第二，具体方案：

- 方案一，引入 Redisson 分布式锁，以货品维度加锁，限制单货品同时仅一个操作执行；并发低，锁竞争激烈，**不推荐高并发秒杀**。
- 方案二，热点库存存入 Redis，通过 Lua 脚本原子增减库存，MQ 异步同步数据库；性能较高

第四，定时任务对账校准缓存与数据库差异。

最终解决了并发库存错乱问题，保障出入库数据准确，同时支撑系统高并发业务访问

（其中的超卖问题）redis+lua脚本的方法。lua中进行获取库存，检查库存，扣减库存的原子性操作，然后利用mq更新数据库。
