## Context

当前 `KnowledgeStore` 使用 `chunkMarkdown` 产出单层 `KnowledgeChunk`，同一个 chunk 同时作为 BM25/向量索引的检索单元和被 Agent 注入的上下文单元。其优点是数据模型简单，但一个长度配置无法同时优化语义命中精度与回答所需的上下文完整性。

现有 `evals/retrieval/knowledge-evidence.v1.json` 是冻结的 source-evidence 基准，证据以原文锚点而非 chunkId 标注，因此理论上可跨切分策略比较；但该语料已用于当前实现的开发与验证，不能作为本次变更最终结论的独立测试集。真实检索评测必须通过 `ensureEmbeddingModelLoaded()`，并显式由 npm lifecycle gate 启动，避免普通 `npm test` 触发模型下载或真实向量推理。

该变更仅影响知识库 RAG；长期记忆和小说索引继续使用各自现有的数据与检索流程，避免扩大数据模型变化的范围。

## Goals / Non-Goals

**Goals:**

- 建立父块保存上下文、子块承担稀疏与向量匹配的知识库数据模型，并保持文档、标题路径与偏移的可追溯性。
- 以子块的 Hybrid 分数选择候选，按父块去重后将父块文本返回给 Agent，防止同一上下文被多次注入。
- 让导入、删除、索引重建和旧索引失效/rebuild 的过程原子地维护父块、子块和两类索引。
- 建立一个与现有 source-evidence 语料、查询和实现调参隔离的冻结测试集，以真实 BGE 路径产出明确口径的 Recall@K 与 MRR@K。
- 通过单元、集成和真实评测命令证明实现正确性，且报告能复现和审计。

**Non-Goals:**

- 不改变记忆索引、小说索引、Embedding 模型、RRF/重排算法或引入云端检索服务。
- 不实现跨父块的上下文拼接、动态上下文压缩、自动超参数搜索或以独立测试集为目标的调参。
- 不把旧知识库索引就地转换为父子结构；检测到旧版本时通过受控重建恢复一致性。
- 不把单次独立评测结果表述为对所有领域或未来语料的泛化保证。

## Decisions

### 1. 知识库采用“父块存正文、子块建索引”的双实体模型

每个父块具有稳定 `parentChunkId`、正文、文档/标题/偏移元数据；每个子块具有独立 `chunkId`、`parentChunkId`、局部正文与局部偏移。父块按 Markdown 标题和段落边界组装，目标是提供一个连贯的章节/段落级上下文；父块过长时再按现有重叠规则拆分。每个父块随后按更小的子块限制与重叠产生多个子块。

稀疏索引和向量存储仅保存子块。父块正文仅持久化一次，降低存储重复，并避免搜索层将大段上下文直接当作相似度特征。

替代方案：为同一文本生成大小两套独立 chunk 并分别检索。该方案缺少稳定父子关联，删除/更新时更容易出现孤立索引项，也无法准确表达“哪个小块命中、哪个大块被带回”，因此不采用。

### 2. 以子块命中排序，映射为父块返回且按父块去重

Hybrid 搜索先保留子块级 sparse/vector/RRF/rerank 分数与召回来源；随后按 `parentChunkId` 聚合，同一父块选择排名最高的命中子块作为代表。最终 top-k 的单位是父块，不是子块，返回父块正文、父块标识及代表子块的命中元数据。排序由代表子块的最终分数决定，稳定的次级排序键保证相同分数时可复现。

替代方案：先选 top-k 子块再简单替换其内容为父块。此方案会让多个子块展开为重复父块，实际可用上下文数少于请求的 top-k，因此不采用。

### 3. 兼容结果契约以父块为主、子块证据为辅

知识库 `KnowledgeHit` 继续保留调用方需要的 `documentId`、`headingPath`、`content`、`score` 与稳定返回标识，并新增/明确 `parentChunkId`、命中的 `childChunkId` 及子块偏移。对于调用方，`chunkId` 语义迁移为“返回的父块 ID”；需要定位精确证据时读取 `childChunkId`。Agent 上下文及工具输出使用父块正文，引用则同时携带父块与命中子块，避免将父块误报为直接匹配片段。

替代方案：破坏性地将 `chunkId` 改为子块 ID。这样会使调用方难以从现有字段获知实际注入文本的归属，并造成引用与内容不一致，因此不采用。

### 4. 索引版本升级采用拒绝旧索引并重建

知识库元数据记录明确的 schema/index 版本。启动、导入前或检索前发现旧版本、父子关联缺失、或父子/稀疏/向量集合不一致时，系统不混用旧数据；将索引标记为需重建，并通过既有重建入口从源文档重新生成全部父块和子块。重建沿用进度报告和批量向量持久化路径。

替代方案：在运行时从旧 chunk 推断父块。旧 chunk 丢失了足够的原始边界信息且会使旧向量与新的子块粒度不一致，不能保证检索正确性，因此不采用。

### 5. 独立评测采用新冻结语料、锚点标注和显式报告

新数据集与现有 `knowledge-evidence.v1.json` 使用不同的 corpus 文件、查询 ID 和证据锚点；每个源文件记录 SHA-256，每个锚点必须在所属源文档中唯一出现。评测映射应以返回父块的正文覆盖证据锚点为准，并在报告中分别给出：所有证据的 Recall@K、required 证据的 Recall@K、以及第一个 required 证据的 MRR@K；未映射证据保留在 Recall 分母且不会获得 MRR credit。

评测命令固定数据集版本、topK、检索配置和模型标识，写出机器可读 JSON 报告。它只能在专用 npm 脚本下运行真实模型，并校验每个语料哈希，防止开发中语料或标签漂移。独立集仅用于最终评测；开发中的单元测试和现有基准仍可用于回归检查。

替代方案：复用 v1 数据集并改名为独立评测。它无法证明与实现调参隔离，因此不采用。

## Risks / Trade-offs

- [父块过大导致注入上下文膨胀] → 为父块设置显式上限、保留标题/段落优先切分，最终按父块去重的 top-k 控制注入数量，并在测试中覆盖超长小节。
- [同一父块多个高分子块挤占候选] → 在截取最终 top-k 前按父块聚合，使用最佳子块作为唯一代表。
- [子块与父块删除/重建不同步] → 集中由 `KnowledgeStore` 维护映射，批量更新索引，并在加载和测试中校验引用完整性与无孤儿记录。
- [旧索引自动迁移造成静默语义错误] → 使用显式版本不匹配检测和完整重建，不执行不可靠的就地转换。
- [独立集太小或证据标签不严谨] → 人工审阅所有锚点，强制唯一锚点与 SHA-256 校验；报告发布时同时保留逐查询诊断，避免只看均值。
- [真实 BGE 评测受模型文件与硬件影响] → 保持 lifecycle gate、加载失败即失败、不允许 mock/fallback，并在报告记录模型标识与运行配置。

## Migration Plan

1. 增加父子块类型、切分器、持久化 schema/index 版本以及完整性校验，同时用单元测试锁定边界和映射行为。
2. 修改知识库导入、删除、重建、搜索与 Agent 结果格式化，使索引只索引子块且返回去重父块。
3. 发现旧版知识库时将其标记为不可检索/待重建；调用既有重建路径从保存的源文档生成新索引并报告进度。保留源文档，因而无需数据丢失。
4. 加入独立语料、证据标签和专用真实评测命令；先运行结构校验和单元测试，再运行真实 BGE 基准生成报告。
5. 验证导入、检索、删除和重建后，完成变更并将实际指标、模型状态和数据集 hash 记录到工作日志。

回滚：代码回滚后，父子索引版本会被旧代码识别为不兼容；通过从源文档重建旧格式索引恢复。源文档是两种索引格式间唯一受信任的恢复来源。

## Open Questions
